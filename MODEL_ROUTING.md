# Маршрутизация по сложности (System One: jev / solar-decide)

Дешёвая модель решает, **какой моделью отвечать**. Решение — одно типизированное
число от 0 до 1, без генерации текста. Ошибка маршрута стоит копейки, поэтому
страховка простая: любая проблема → `null` → работаем ровно как раньше.

Тем же запросом решаются ещё три вещи (state один, цена та же):

| Вопрос | Тип | Что заменяет |
|---|---|---|
| `archetype` | `choice` (8) | `pickResponseArchetype()` — раньше `Math.random()` |
| `ask_question` | `noul` | `decideQuestionPolicyForThisTurn()` — раньше 12% случайно |
| `needs_memory` | `noul` | задел для стадии 1 (пока только логируется) |

Порог вопроса — 0.5. Приоритеты: режим `ASK_ME` важнее модели, модель важнее случая.
Инструкции архетипов дословно совпадают с прежними строками из `ui.js` — промпт
стадии 2 не меняется, меняется только способ выбора.

## Контракт

`POST {base}/v1/systemone` (Hydra), тело:

```js
{
  model: 'jev-1.14',              // или 'solar-decide'
  state: { message, recent },     // одна общая точка контекста
  questions: {
    complexity:    { type: 'score', instructions: '…', criteria: [10 уровней] },
    needs_memory:  { type: 'noul',  instructions: '…' }
  }
}
```

Ответ: `answers.complexity.score` (0…9) и `answers.needs_memory.noul` (0…1),
плюс `confidence` и `usage`. Выходные токены бесплатны у обеих моделей.

| Модель | Вход | Контекст в каталоге Hydra |
|---|---|---|
| `jev-1.14` (TypeSafe) | 2,70 ₽ / 1M | 260 000 |
| `solar-decide` (Upstage, beta) | 1,00 ₽ / 1M | 500 000 |

Переключатель провайдера: `localStorage.chatbot_systemone_provider` = `jev` | `solar`
(по умолчанию `jev`). Ключ на сервере: `HYDRA_API_KEY` в `/api/systemone`.

## Уровни и модели

| Сложность | Уровень | Куда идёт ответ |
|---|---|---|
| `< 0.5` | easy | цепочка OpenRouter (`nvidia/nemotron…`), Hydra — только если цепочка упала |
| `0.5 … 0.79` | medium | Hydra `glm-5.2` |
| `≥ 0.8` | hard | Hydra `hydra-gemini-pro` |

Пороги — в `SYSTEMONE_CONFIG.thresholds` (`jev.js`). Модели уровней — в
`pickRouteByComplexity`, там же меняются без правок остального кода.

## Когда маршрут не работает

- Нет платного провайдера (`isSmartMode()` и `isFullHydraMode()` ложны) — все ходы
  идут прежним путём: в бесплатном режиме менять нечего.
- Выключатель: `localStorage.chatbot_route_complexity = '0'`.
- `jev.js` не загрузился — `resolveTurnRoute` не вызывается вовсе.
- Сеть, таймаут (25 с), мусор в `answers`, `score` не число — `null`, прежняя модель.

## Стоимость

Один запрос ≈ 400–800 входных токенов ≈ **0,001–0,002 ₽**. Замер в коде:

```js
getSystemOneStats()
// { calls, errors, cacheHits, byProvider, tokens, provider, estimatedRub }
```

Одинаковые состояния кэшируются (до 200 записей), повторный ход по тому же
сообщению денег не тратит.

## Совет вопросов (council.js)

Решения хода принимаются **одним** запросом System One. Раньше их было два
(маршрут и темы памяти), а часть решений вообще жила на `Math.random()` в `ui.js`.

| линза | вопросов | что решает |
|---|---|---|
| `route` | 4 | сложность (`score`), форма ответа (`choice`), вопрос в конце (`noul`), нужна ли память (`noul`) |
| `safety` | 2 | дистресс и кризис (`noul`) |
| `greeting` | 1 | приветствие или светская реплика (`noul`) |
| `memory` | 3 | прямые темы (`choice`), уместность ассоциации (`noul`), латеральная тема (`choice`) |

Итого **10 вопросов из 32** — остальные слоты свободны под следующие линзы
(цели, извлечение).

Линза — это данные, а не ветка кода:

```js
COUNCIL_LENSES.goals = {
    questions(ctx) { return { goal_stuck: { type: 'noul', ... } }; },
    apply(answers) { return { stuck: answers.goal_stuck.noul >= 0.6 }; },
    fallback: { stuck: null }
};
```

`buildCouncilQuestions(ctx)` собирает вопросы всех включённых линз,
`applyCouncilAnswers(answers, ctx)` раскладывает ответы обратно, `resolveCouncil`
делает сам вызов. Новая линза — это одна запись в реестре.

**Деградация.** Браузер ждёт ответ 25 секунд, продовый proxy ждёт Hydra 20 секунд.
Если запрос с латеральной линзой получил обычную ошибку API, совет один раз повторяется
без `need_lateral` и `lateral_cloud`: необязательная ассоциация не должна ломать
основные решения. После таймаута второй запрос не запускается, чтобы не удваивать
ожидание. При полном отказе → `null`, и ход идёт нейтрально: без архетипа, без вопроса,
без памяти, маршрут — прежняя модель. Реальная причина доступна в
`getLastCouncilError()` и спойлере.
Случайных запасных вариантов больше нет: поведение должно быть воспроизводимым.
Единственное исключение — регулярка `detectUserDistress` остаётся **вето** поверх
вероятностей: пропустить кризис из-за упавшей сети дороже, чем лишний раз
поддержать человека.

**Пороги** — `COUNCIL_CONFIG.thresholds`: `askQuestion 0.5`, `distress 0.55`,
`crisis 0.4`, `greeting 0.55`. Пока нет журнала исходов, калибровать нечего,
поэтому пороги живут в коде.

**Что удалено** вместе с переездом: `resolveTurnPlan`, `resolveMessageRoute`,
`selectCloudsForTurn`, `pickResponseArchetype`, `decideQuestionPolicyForThisTurn`.
Второго вызова jev в ходу нет — это проверяется тестом.

**Наблюдаемость.** `window.lastCouncil` — весь ответ совета: решения, вероятности,
вопросы и сырой ответ модели. Спойлер под ответом не менялся: он по-прежнему
показывает темы и решение по ходу.

## Облака памяти: выбор темы и фоновая стадия разбора

Перед сборкой контекста jev решает, **какие темы памяти поднять** в этом ходу.
Тема (облако) — весь срез профиля: факты, черты, хронология, люди, гипотезы и
пробелы, помеченные одним `cloud`. Выбор — один запрос на ход с двумя контурами:
прямой `clouds` ищет темы по существу, а `lateral_cloud` — отдельную тему для
возможной аналогии. Второй контур включается только при `need_lateral >= 0.45`,
не дублирует прямую тему и отключается кодом при distress/crisis.

Раньше на каждую тему шёл свой `noul`: 24 темы — 24 вопроса из 32 доступных, и на
всё остальное в ходу оставалось восемь. Теперь все темы занимают по одному варианту
в двух choice-вопросах (прямой и латеральный), а ответ приходит распределением — из него видно и «какая нужнее всего», и «какие ещё
близкие». Варианты нумеруются по позиции (`cloud_0`, `cloud_1`, …), потому что id
облака может содержать что угодно; последний вариант — `none` («ни одна тема не
нужна»).

Как из распределения получается выбор (`pickCloudsFromDistribution`):

| правило | значение |
|---|---|
| Anchor | лучшая тема берётся при `p₁ ≥ 0.08` |
| остаточная масса | `max(0.05, 1 − p₁ − p_none)` |
| соседние темы | `pᵢ ≥ max(0.04, residualMass × 0.28)` |
| максимум | `3` прямые темы |
| стоп по «ничего» | если `none ≥ 0.5` и не ниже лучшей темы — память не поднимается |

В Insight Mode после прямого и латерального выбора может сработать один
**Serendipity Slot**: шанс `0.30`, только ещё не выбранные темы с `p = 0.025..0.10`,
взвешенный выбор с весами `√p`. Слот не создаёт новых вероятностей и не может вытянуть
нулевую тему. При distress/crisis он подавляется вместе с латеральной ассоциацией.
Роль `serendipity` попадает в ту же отдельную зону бокового зрения, что и
`lateral_bridge`, а не в прямой контекст.

- Дёшево: тот же один вызов, что и раньше, ≈ **0,005 ₽ / 0,3–0,5 с** против
  ≈ **0,15–0,2 ₽ / 1,5–4 с** у сжатия досье. Два choice-вопроса вместо вопроса
  на каждую тему — число вопросов больше не растёт вместе с числом облаков.
- Спойлер под ответом показывает не только поднятые темы, но и всё распределение
  (`🎲`-чипы с вероятностями, верхушка из 10), порог и правило отсева.
- Контекст второй стадии — компактное Always-On Core (стиль, до пяти черт и до
  трёх гипотез с дедупликацией) плюс выбранные облака, по `itemsPerCategory = 12`
  записей на категорию. Прямые и латеральные темы разделены: латеральный блок
  разрешено использовать только для уместной аналогии, иначе игнорировать.
- Время исходного высказывания, тип и дата события сохраняются в облачном
  контексте; относительные даты не привязываются заново к текущему дню.
- Флаг: `localStorage.chatbot_cloud_memory` (`'0'` — выключить), по умолчанию включён.
- Порог входа — **две темы с записями**. Пустые темы (в том числе пустое «Разное»)
  не считаются и вычищаются при чтении: иначе «5 облаков» в хранилище означали бы
  одну реальную тему.
- **Одна тема с записями** — это вся память: она поднимается напрямую, без вызова
  jev. Раньше такой аккаунт уходил в сжатие досье и платил за него.
- Ни одной темы с записями, jev не ответил, поднятые темы пусты или ошибка выбора —
  работает прежнее сжатие досье. Причина запоминается в `lastCloudSkip` и видна в
  спойлере под ответом строкой «Почему не облака: …».
- Превью «мыслей» (`micro_opening`) убрано: интерфейс беднее, зато без лишней
  генерации.

### Кто ведёт облака

**Не извлечение и не пользователь.** Извлечение (`extractFactsInformation` и др.)
только записывает факты, черты, события и людей — поля `cloud` в его схемах нет.
Названия тем, их наполнение, описания, слияние дублей и переименование — работа
отдельной фоновой стадии разбора («сон»), `runCloudConsolidation()` в `analytics.js`:

1. получает темы с описаниями и счётчиками плюс записи (сначала без темы, потом
   уже разложенные, до `maxItemsPerPrompt = 40`) и их текущие темы;
2. одним вызовом модели просит: разложить новые записи (`placements`), добавить
   общую тему уже разложенной записи (`links`), создать тему (не больше двух за
   проход), слить дубли (`merges`), переименовать неудачные имена (`renames`),
   обновить описания;
3. применяет ответ сам: слияния → переименования → описания → раскладка;
   всё, что не разложилось, уходит в «Разное», пустые темы удаляются.

Запускается после извлечения, не в ходу ответа. Повод: накопилось
`minUnassigned = 4` записи без темы, либо тем ещё нет, либо прошли сутки
(`refreshAfterMs`) и записей не меньше `refreshMinItems = 8`. Пауза между
попытками — `cooldownMs = 3 мин`, в том числе после неудачной: сбой не повторяется
каждый ход. Стоимость прохода ≈ **0,01 ₽** (hydra-gemini, вход ~1k токенов),
то есть разбор дешевле одного сжатия досье и происходит редко.

### Несколько тем у одной записи

Запись может принадлежать нескольким темам: «работаю в Сбере» — и «Работа», и
«Карьера». Хранение: `item.clouds = [id…]`, `item.cloud` остаётся первой
(основной) темой для совместимости со старыми записями, где список не писался.

- Стадия ставит набор тем новой записи (`placements.clouds`, до трёх) и может
  добавить вторую тему уже разложенной (`links`) — прежние темы при этом не
  отбираются.
- Выбор тем использует то же распределение прямого и латерального choice.
- Сборка контекста дедуплицирует записи по id: если подняты обе темы, запись
  попадает в промпт один раз — под первой по порядку выбора темой.
- Счётчики тем считают запись в каждой теме, поэтому сумма по темам больше числа
  записей; заголовок вкладки показывает уникальное число (`countUniqueCloudItems`).
- Слияние тем переписывает все ссылки и схлопывает дубли в массиве.

### Слияние, деление, удаление

Всё делает стадия разбора, в одном вызове, по своим правилам:

| Что | Как | Ограничения |
|---|---|---|
| слияние | `merges: [{from, into}]` — записи переезжают, ссылки переписываются | исходная тема исчезает, если опустела |
| деление | `reassign: [{index, clouds: [...]}]` — у записи переписывается набор тем | не больше `maxReassignPerPass = 20` за проход; исходная тема обязана сохранить хотя бы одну запись, иначе перенос отклоняется (полный переезд — это `merges`) |
| удаление | отдельного действия нет: тема удаляется, когда после слияний и переносов в ней не осталось записей (`pruneEmptyClouds`) | «Разное» не удаляется никогда |
| переименование | `renames: [{from, to}]` | дубль имени не принимается |

Всего тем — `maxClouds = 24`, включая «Разное» (это обычное облако со служебным
id). Если лимит исчерпан, `ensureCloud` возвращает `null` и новая тема не
появляется — стадия вынуждена раскладывать по существующим. jev спрашивает не
больше `SYSTEMONE_CONFIG.maxQuestions = 32` вопросов за ход, так что 24 темы
помещаются с запасом.

Кнопка «Разобрать сейчас» в интерфейсе запускает проход принудительно: она
обходит паузу `cooldownMs`, но не лимиты. Один проход берёт не больше
`maxItemsPerPrompt = 40` записей и создаёт не больше двух тем, поэтому большую
старую память придётся разобрать несколько раз подряд — вкладка показывает,
сколько записей ещё без темы.

В интерфейсе вкладка «☁️ Облака памяти» — **только просмотр**: имена, описания,
счётчики и время последнего разбора. Ручного переименования нет: это работа
стадии. Есть выключатель выбора тем и кнопка «Разобрать сейчас» — она лишь
просит стадию отработать вне очереди (`force`), а не правит данные.

## Защита от вымысла

Персонаж фильма — не человек из жизни пользователя, но цитата при этом
настоящая: «его младший брат погиб на войне» действительно сказано
пользователем. Проверки «это слова пользователя» мало — нужна проверка, о чём
эти слова.

Извлечение (факты, черты, события, люди) теперь пропускает только цитаты,
которые не относятся к вымышленному миру:

| правило | что делает |
|---|---|
| `fictionFrame(quote, history)` | ищет маркер вымысла в сообщении с цитатой (фильм, сериал, персонаж, сюжет…) или сильный маркер в предыдущем сообщении; если сообщение уже ушло из истории — судит по самой цитате |
| `nameInFictionFrame(name, history)` | имя всплыло в разговоре о вымысле → контакт не создаётся |
| `aboutSomeoneElse(quote)` | третье лицо без первого («его брат погиб») — не факт о пользователе |

Правила действуют только на **новое** извлечение. Уже записанные персонажи
убираются кнопкой «🧽 Убрать вымысел» в шапке базы знаний: `findFictionPollution`
ищет записи, у которых **все** цитаты пришли из вымысла, `purgeFictionPollution`
помечает факты/черты/события `superseded: true, supersededReason: 'fiction'`,
а контакты удаляет. Записи без цитат не трогаются — доказательств против них
нет.

Плюс ручное удаление: крестик `✕` у каждой записи (`deleteMemoryItem`, помечает
`supersededReason: 'manual'`) и у каждого контакта (`deleteContact`). Автоматика
ошибается в обе стороны, поэтому последнее слово остаётся за пользователем.

## Проверки

`tests/clouds.test.cjs` — дедупликация имён (регистр, ё), «Разное», изоляция контекста
по выбранным облакам, Always-On Core, прямой и латеральный choice на все темы, Anchor 0.08 и residual-отсев 0.28 для прямого контура, максимум 3 прямые темы, Serendipity Slot с детерминированными тестовыми бросками, один запрос на ход, порядок
«облака → длина → сжатие», отсутствие `micro_opening`, отсутствие облаков в схемах
извлечения, раскладка и называние тем стадией разбора, несколько тем у записи,
дедупликация в контексте, добавление общей темы через `links`, деление темы через
`reassign` и защита от её опустошения, слияние дублей и переименование, лимит тем,
пауза после прохода и после сбоя, вкладка только для просмотра.

`tests/hygiene.test.cjs` — персонаж фильма не становится контактом, брат героя не
становится фактом о пользователе, настоящие люди и факты проходят как раньше,
третье лицо без первого отклоняется, чистка находит и убирает уже записанное
(контакт удалён, факт помечен устаревшим, в промпт больше не идёт), записи без
цитат не трогаются, кнопки чистки и ручного удаления на месте.

`tests/routing.test.cjs` — контракт запроса (четыре вопроса), переключение провайдера,
границы 0.5 / 0.8, нормализация шкалы, порог вопроса 0.5, совпадение архетипов с
прежними строками `ui.js`, кэш, таймаут, отказ сети, подстановка модели в стриминг,
порядок «OpenRouter → Hydra» на лёгком маршруте, гейт по режиму и флагу.

Дев-сервер отвечает на `/api/systemone` демо-значением по грубой эвристике
(`SYSTEMONE_DEV_FORCE=0.85` фиксирует сложность) — чтобы все три уровня можно было
увидеть без ключа. В проде за это отвечает сама модель.
